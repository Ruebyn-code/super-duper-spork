# Order history

Orders display a short company/location number, for example **SGR-MER-0001** for Souvlaki GR, Mernda. Company codes use initials, filling from the final word (Souvlaki GR → SGR); location codes use the first three letters/numbers. Codes are uppercase and normalised, with short names padded with X. Missing legacy names use CMP/LOC. The sequence is at least four digits and grows beyond 9999. Live orders and manually recorded past orders share it. Locations or companies with identical abbreviations share a sequence within their network so numbers stay unique.

Numbers are reserved durably before saving or sending. Retries retain the same number, deletion never recycles one, and interrupted saves can leave gaps. Renaming a company/location changes the prefix for future orders only. The first run after this update gives existing orders numbers in original save order, including deleted records, in a separate display registry. Legacy order files stay untouched, and no email is resent. UUIDs remain the internal IDs for links, files, retries and provider idempotency. History filters accept both the short number and the original UUID. Supplier templates’ Order reference and sender confirmations use the short number for new emails; previously sent messages remain unchanged.

Open **Ordering → Order history**, or use the Order history link above the catalogue. History shows saved orders for the selected location, including orders recorded by other staff there. Search by stock item, supplier, reference or order ID; filter by supplier and original date. Details retain saved item names and units, and show effective unit prices alongside original prices when stock prices have updated. Sending states describe submission to a service or a platform handoff, rather than confirmed supplier receipt.

**Record past order** is available to users with `orders.place`; browsing requires `orders.view`. Choose the original order date, then browse the same compact supplier/category cards as Ordering, with product photos, names, SKUs, unit amounts, prices and Qty / + Add controls. Search, supplier filters, Cards/List views and 25-item pages retain your draft quantities. Repeated additions combine into one order item. Use the popup footer’s **Order items** total to jump to the selected items, where quantities and actual historical unit prices remain editable; **Choose stock** returns to the picker. Browsing, quantity drafts, filtering and previews do not save anything. Search Enter never submits, and Enter on a card quantity adds only that item. Add an optional order/invoice reference and notes, check the displayed total, then choose **Save to history**. Blank prices remain pending; zero is a known zero price. The original quantities may differ from today's minimum order rules. Record each stock item once per order.

A manual entry represents an order already placed outside OpStack. It sends no supplier email, order confirmation, SMS or platform request, and does not alter the catalogue, stock count snapshots or the current cart. It enters the normal cost, budget and stock-usage calculations on its original Melbourne date. Existing Sunday rules still apply: quantities belong to that Sunday's usage week, while order costs fund the next financial week. The separately saved recording time and staff identity identify when the missing order was entered.

To correct a placed or manually recorded order, open **View order → Edit order**. Change items using the same category cards, or edit quantities, unit prices, reference and notes in Order items, then choose **Save changes**. The original order date remains fixed. Blank unit prices remain pending; zero is a known zero price. Existing item names, packs and suppliers retain their saved snapshots, including removed stock; added items use the current company catalogue with a pack/supplier check at save time. Edits update history, order costs, ordering budgets and stock usage, preserving stock count snapshots and invoice-only weekly expenses. Saving sends no supplier email or order confirmation and does not change the current cart or catalogue prices. Contact the supplier separately to change an order already sent.

Edits require `orders.view` and `orders.place`, CSRF and an exact company/location match. Orders still being sent cannot be edited. Received suppliers retain their receipt audit and must keep at least one item; correcting their quantities/prices is allowed. Added suppliers start unconfirmed and untracked until explicitly confirmed. A stale order, stock-price or delivery revision rejects the save while retaining the draft. **Reload latest** explicitly discards that draft; an uncertain save freezes its details for a same-request retry.

Private `orderEdits` entries in the company catalogue contain the before/after snapshots, stable edit request ID, revision, actor, scope and time. They commit through the same catalogue queue as price changes, deletion and delivery updates. Original UUID files, dates, request fingerprints, supplier payloads and confirmation records remain unchanged. Native readers layer the latest saved correction and later stock-price adjustments; a manual correction takes precedence over earlier price adjustments. Future price changes use the corrected effective item membership at each location. Public catalogue responses omit this audit; history exposes only the edit revision, optimistic token and last editor/time.

Stock price changes can update effective prices as described below. A save retry reuses its UUID and canonical details, so concurrent retries create one record. Reusing a request UUID for different details, a normal order or another staff member is rejected. If a network failure leaves the save uncertain, the form retains its request and freezes the entered details for an explicit retry; closing it refreshes history so the user can check for the saved order.

To remove an order, open **View order → Delete order**, review the warning, then confirm **Delete order**. This is available with `orders.place` for both manually recorded and platform orders in the selected location. Cancel or Escape leaves the order untouched. Deleting removes the order from history, search, cost/budget reports and stock-usage calculations; it does not change count snapshots, catalogue prices or the current cart. It does not cancel a supplier order or recall an email: contact the supplier separately if cancellation is needed. Orders still being sent must finish sending before deletion.

Deletion retains a private record with `status: deleted`, `deletedAt`, `deletedById` and `deletedBy` so concurrent requests or a lost-response retry cannot recreate or resend the order. Repeated authorised deletes succeed without changing the original audit. Deleted UUIDs remain reserved; attempting to record or place the same UUID again is rejected. The shared order reader excludes deleted records, including after its cache has been warmed. These private records and audit fields are unavailable through history or the older order-detail endpoint.

The APIs are `GET/POST /api/order-history` and `GET/PUT/DELETE /api/order-history/:id`. Edit and delete requests include the displayed `companyId` and `locationId`. Lists return 25 records per page, location/company-scoped summaries and the current `canRecord`/`canEdit`/`canDelete` capabilities. Detail responses omit phone numbers, provider configuration, handoff data, internal owner identifiers and request fingerprints. The older `/api/orders/:id` endpoint keeps its owner-only policy. All writes require current order permissions, CSRF and an exact company/location match. Mandatory Comms reading and the persistent navigation shell apply to the page.

Records use the existing UUID order files with `status: requested`, `source: manual_history`, `orderDate`, an original-date `createdAt`, and separate `recordedAt`/`recordedBy` attribution. Item identities and supplier names are resolved from the selected company's catalogue on the server. Prices are submitted as exact integer cents. Native readers therefore include historical entries once without additional report stores or recalculation writes.

When an existing stock price changes in stock settings or an explicitly confirmed invoice, OpStack applies it to the **latest order containing that item at each location** in the same company. The newest placed date wins, then recording time and UUID, matching the history list. Different items may update different orders. Deleted orders are excluded. Only the matching item price and derived totals change; quantities, original dates, other item prices and stock counts keep their saved values. A known zero is applied; an unknown catalogue price does not erase a saved price. Explicitly different packs or suppliers are skipped without guessing a conversion or updating an older order instead.

History marks affected orders **Stock prices updated**. Details show the update time, original total and each affected item's original unit price. Order totals, ordering budgets, Home order metrics and order reports use the revised totals. Weekly financial Cost of goods continues to use invoices only. Previously sent supplier messages and sender confirmations retain their original contents; a price change sends no email and does not place another order.

Private `orderPriceUpdates` records in the company catalogue save exact target order/item IDs, before/after prices, time, staff identity and source (including invoice ID where applicable), atomically with the changed catalogue price. Original UUID order files remain untouched. Reads apply those durable adjustments without rewriting snapshots or retargeting to newer orders; deletion does not move an earlier adjustment to another order. Request fingerprints, original payloads and idempotency keys remain stable across retries and restarts. Public catalogue responses omit the private audit; history exposes only the relevant original prices and update time.

Order details now include **Delivery tracking** for each supplier. New orders keep
an estimated delivery date from the location's current schedule. Use **Confirm
ordered** for orders placed externally or not confirmed by a sending service,
**Change delivery date** to correct an outstanding estimate, and **Mark received →
Confirm received** when that supplier's full delivery arrives. Multiple-supplier
orders can be part received. Order placing permission is required for these actions.

Receipt actions update separate revisioned audit records in **data/order-receipts/**,
not the original order or count files, and never resend a supplier message or
change financial totals. Historical orders start untracked; recording an old
receipt only updates history. Confirming an outstanding order with a future date
includes it in delivery-based stock planning. See [Delivery planning](supplier-delivery-planning.md).
