# Labels

Open **Prep & labels** in the main navigation, or **More → Prep & labels** on a phone (the page was called Labels; its `/labels` address, IDs and permissions are unchanged). It is a separate page. Each company has its own label templates and label settings. Label history is limited to the selected location and the user's current access.

Head Office can manage company label templates/settings by default. All signed-in built-in staff roles can view and print labels. Settings → Permission levels has separate **Labels**, **Print prep labels** and **Manage prep labels** grants. Existing customised roles keep their permissions; grant the new controls explicitly where needed. Managing the shared company library/settings also requires access to all of that company's active locations.

## Create label templates

Choose **Add label template**, or **Template library → All templates** to include inactive templates. Use the category sidebar, search and sort controls to find labels. Choose a category when saving a template, or select **New category…** to add one. The same item name can be used in different categories. Templates without a category appear under **Uncategorised**. Open a card’s **… → Edit label template** to change it. Enter the name, approved shelf life in hours or days, and an optional label note. Save. Turn off Active label template in the editor to archive it. Shelf lives start blank: Opstack does not infer food safety storage periods. Use the company's approved procedures. Editing or deactivating an item does not rewrite existing label batches.

## Design each template

The template editor uses a modern two-panel layout. **Template details** sits in a lightly tinted left panel with each field's label on its outline and an **Active label template** switch. The designer toolbar shows the media size and padding as chips, with icon buttons for Snap, Preview and Reset beside **Add a field**. Field rows show an icon tile, with the selected row marked in the company colour, and the move, text size, Undo move and **Edit field** controls sit together in one floating bar below the label (pinned to the bottom of the designer on phones). These are styling changes only; every control behaves as before.

The **Label designer** uses a clean dotted workspace with the actual paper proportions, a compact toolbar and a selectable Fields list. The toolbar shows the current media dimensions. Press **Add a field**, then choose its type from the icon menu. Drag a field to position it; drag any edge or corner to resize it. Fields can align with other visible fields, with guides while dragging; page edges and the page centre are not magnetic. Arrow keys allow precise positioning. The editor uses the selected company’s primary and secondary colours. The whole paper scales to fit the available screen; Save and Add a field stay visible while template details or field options scroll in their own panels. Use the adjacent guide icon for instructions. Click a field on the canvas or Fields list to select it without opening a popup. Double-click, press Enter or use Edit field to open its transactional editor. Selected fields have larger resize targets. Use the move arrows (Shift for larger steps), text-size buttons and Undo move for quick changes. Snap is on by default and moves or resizes fields in 0.5 mm micro-steps, with close field alignments taking priority. The designer does not magnetically snap fields to the page edges or page centre. The grid follows the actual media dimensions. Snap can be toggled, and holding Alt bypasses both the micro-grid and alignment guides during a drag. Pointer movement is drawn once per animation frame; Escape, cancelled touch gestures or lost pointer capture restore the starting geometry. These controls affect only the template draft. The list shows field sources, sizes and visibility. On smaller screens it collapses below the artwork. Preview hides editing boxes without changing the artwork or saving a draft; Back to editing restores them. Reset asks before replacing the current draft with the default layout. Arrow keys move a focused field by 1% (Shift by 5%), Enter opens formatting and Delete removes it. An empty editor can be built up again, but a saved template needs at least one field.

Click a field to open **Edit field**. Change the source, text or default value, size slider, fit/wrapping, alignment, letter case, black/white inversion, bold, italic, underline and font. Date sources have date/time formats. More options contains the text prefix, precise point size and percentage positions, visibility and required dynamic values. **Done** keeps changes in the template draft; Close/Escape cancels that field’s changes. **Save label template** commits the whole design. The company-colour editing tint, alignment guides, borders and resize handles are not printed. Reset label design restores the default field layout in the unsaved draft.

Field types include Static Text, Name, User, Location, Current Date & Time, Preparation Date & Time, Ready Date & Time, Discard Date & Time, Shelf Life, Dynamic Text (On Label), Dynamic Text (On Print), and the template note. Static text stays the same for future batches. Name, User and Location use saved template/current server context. Current Date & Time captures the server’s batch-creation time; reprints keep it. Discard time uses the approved shelf life. Shelf Life displays its configured number and unit.

Ready Date & Time uses an explicit **Ready after** amount and period saved on the template. Minutes/hours use elapsed time; days keep the same Melbourne wall time across daylight saving. Zero is allowed if explicitly entered. Ready time must not fall after discard time; Opstack does not infer a ready delay.

Dynamic Text (On Label) is changed by clicking its highlighted area on the print preview. Dynamic Text (On Print) appears as an entry in the print form. Both may have a field name, default value and a required-entry option. Values apply to the current batch and do not change the shared template. Existing batches retain their original design, category, current/prep/ready/discard times and entered values for reprints.

## Prepare and print

Click an active label card to open its primary-tinted **Print labels** popup. The clicked card selects the template; the popup has no template selector or separate Use by row. Enter the preparation date/time and number of copies (1–100), then review the label. Use the secondary-colour − / + buttons to adjust the count, or type it directly. The compact popup puts the paper size beside its heading, uses short text-entry rows, and keeps shelf-life/timezone details inside the expandable printer guide. It keeps print actions visible while extra fields scroll, and scales the whole label into its preview without cropping or changing its printed size. The use-by time is calculated from the saved item settings. Hour-based shelf life adds elapsed hours. Day-based shelf life keeps the same Melbourne time on the following date, including daylight-saving changes; skipped times use the first valid minute afterwards and repeated times use the later occurrence.

The default label shows item name, location, preparation time, use-by time, signed-in staff name and any note. Preparation time is an entered value; the record also keeps a separate server creation timestamp. Staff names, location and use-by calculation are resolved on the server. Concurrent item/settings changes require refreshing before a new batch can be created. Retries with the same request reference do not duplicate a batch.

Default media is **50 × 25 mm**, with **203 dpi**. If the printer is a 300 dpi model, select 300 dpi in **Label settings**. At 300 dpi, printable width is limited to 54 mm; at 203 dpi, it is 56 mm. Settings support 20–150 mm label height.

Labels print **only by Bluetooth**; the system print dialog and Zebra file download have been removed. **Print labels** sends the batch straight to a Bluetooth Low Energy label printer through the browser's Web Bluetooth support (`public/label-bluetooth.js`). Connecting is always explicit: **Connect** (or the first **Print labels**) opens the browser's own device chooser listing every nearby Bluetooth device (`acceptAllDevices`), because printers such as the Zebra ZD411 usually advertise their serial number (for example `D4J…`) rather than a recognisable name or service. The chooser opens the known label-printer services (Zebra Link-OS BLE parser, Zebra `0xFE79`, and common generic BLE printer serial services). After connecting, the known write characteristic is used if present; otherwise the first writable characteristic on any service the browser allows. A failed first GATT connection is retried once. Errors keep a plain explanation and append the browser's own reason (for example `NetworkError: Connection attempt failed`) to help diagnose a printer that won't connect; a printer still connected to another phone or computer is a common cause. Nothing reconnects or prints on page load, and the connection lasts only while the page is open. The batch is created first through the normal idempotent batch API, then its frozen raster is sent as ZPL with ASCII compression (repeat counts, `,` trailing zeros and `:` repeated rows; `^GFA` byte counts stay uncompressed totals), in ordered chunks of up to 180 bytes (20 bytes for write-without-response channels or after a first-chunk failure). Before sending, a Zebra printer connected on the Link-OS parser channel is asked (read-only, once per connection) for its print resolution with the Set-Get-Do query `! U1 getvar "head.resolution.in_dpi"` on its read channel (`38eb4a81…`). If it reports 203 or 300 dpi and that differs from the company Printer settings, the same layout is drawn at the printer's resolution (width capped at 56/54 mm) so the label keeps its real size in millimetres instead of printing about 1.5× too large and cut off (300 → 203) or about two-thirds size (203 → 300); the saved batch snapshot is unchanged and the status message asks staff to update Printer settings to match. Printers that cannot answer within 2.5 seconds print exactly as before. If sending fails, the saved batch stays in Recent batches, where **Print again** resends it unchanged. A successful send means the printer accepted the data, not that labels physically printed. Web Bluetooth works in Chrome/Edge on Android, Windows, Mac and ChromeOS over HTTPS; iOS/iPadOS browsers (Safari, and Chrome/Edge on iOS) do not support it, so printing is disabled there and the popup says to use a Web Bluetooth browser app such as Bluefy, or an Android device or computer. The persistent shell's content frame allows `bluetooth`.

The app does not install a USB/network bridge or use AirPrint. The preview and ZPL generation can be tested without hardware; check an actual label on the printer to confirm media calibration and margins.

## History and storage

**Label history** shows the latest 25 created batches at the selected location. It records creation of the label data, not physical printer delivery. Print or download an earlier batch using its original name, shelf life, dimensions, preparation/use-by times and staff attribution.

The network's `prep-labels.json` contains company items, settings and immutable batch snapshots. Include it in backups and migrations. Company/location/permission checks and required-reading rules apply on every API request; label generation does not change stock counts, orders, sales or expenses.

**Padding (mm)** reserves a physical white border inside the label. New templates start at 1 mm; choose 0–5 mm in 0.25 mm steps. Field percentages describe the remaining inner area, so all fields, canvas overlays, On Label click targets and raster/ZPL output stay aligned. Existing templates and historical batches without padding retain their original rendering; padding applies only through an explicit template save, and old batches keep their frozen layout. Older writers that omit the new property retain saved padding, while an explicit zero removes it.

## Card layout and template photos

Each Labels card shows the template name and ⋯ menu in a white bar at the top, with the label preview underneath; the category pill sits in its own row above the preview so it never covers the label.

Template managers can add one optional **photo** per template in the editor's Template details (**Add photo** / **Change photo** / **Remove**). The photo is centre-cropped in the browser to 16:9 (up to 1200 × 675 JPEG) and stays a draft until **Save label template**: the template saves first, then the photo through the revision-checked `PUT`/`DELETE /api/prep-labels/items/:id/photo` (same template-manager rule as editing: `prep.manage` plus every active company location; JPEG/PNG/WebP up to 2 MB, checked by file signature). Files are stored privately under `prep-label-photos/<companyId>/`, served with `GET` to anyone with prep label viewing in the same company (private, no-sniff, sandboxed), and replaced files are removed. Ordinary template saves keep the existing photo. Cards show the photo behind a smaller label preview. Photos are for finding the right label only: they are never printed or copied into batches.


## Shared designs

One label design can be used by many label templates. In the label template editor, **Design** (in Template details) offers:

- **Own design (this label only)**: the default; the label keeps its own layout.
- **A shared design**: links this label to that design. The designer loads the shared layout, and saving changes to it updates every label linked to that design. The note under the chooser says how many other labels share it.
- **Save as a shared design…**: names the current design and saves it as a shared design that this label (and later others) link to.

Each label keeps its own name, shelf life, category, note, photo and active switch. Shared designs are company-wide and managed by label template managers (manage permission plus access to every active company location). They are stored in `prep-labels.json` under `designs` (up to 200 per company, names unique ignoring case). Linked templates store `designId` and no layout of their own; reads and saves return the design's layout with `designId`, `designName` and `designRevision`. Saving a linked label sends `design:{id,revision}`, and a changed layout updates the design only when its revision still matches (otherwise 409). Older writers that omit `design` keep the link; `design:null` turns the current layout into the label's own copy; `design:{name}` creates a shared design from the layout.

**Rename** and **Stop sharing** (`PUT`/`DELETE /api/prep-labels/designs/:id`, revision-checked) appear beside a chosen shared design. Stopping sharing deletes the shared design but every linked label keeps a copy as its own layout (their revision goes up). Printed batches snapshot the design's layout together with `designId`/`designRevision`; printing with a stale design revision is refused so the preview always matches the label. Cards show a small marker with the shared design's name.
