# Stripe location and user billing

Console → Billing is available only to OpStack platform owners. It replaces the GoCardless connection. Existing GoCardless snapshots remain available in Monthly report → Collections → Archived GoCardless. The app no longer calls GoCardless or processes its webhooks. **Cancel/finish existing GoCardless subscriptions in GoCardless before starting Stripe subscriptions.** Removing the connection does not cancel external billing.

## Guided setup

Console → Billing shows five saved steps, with separate Sandbox and Live progress. Continue explicitly saves the completed step; Back and the step buttons retain unsaved input. Save progress saves without moving on. The app does not persist credentials, billing addresses or plan drafts in browser storage. Reopening derives progress from saved server evidence; a replaced key requires another connection test. Existing billing continues under its existing approvals while an owner reviews setup.

1. **Connect.** Activate the business's Stripe account and start with Sandbox. Paste the matching `sk_test_…` secret key and choose **Save & connect**. This saves then tests it with the existing provider sync. Live requires a separate `sk_live_…` connection. Keys stay masked and private in `DATA_DIR/opstack/stripe.json` (0600).
2. **Notifications.** Set `APP_ORIGIN` to the public HTTPS app origin if no webhook address appears. Copy the address into a Stripe webhook for Your account and snapshot events. Select `checkout.session.completed`, `customer.subscription.*`, `invoice.*` and `charge.refunded`. Use endpoint API version 2024-06-20 if offered. Paste its matching `whsec_…` signing secret, then **Save & continue**. Saving a secret means configured; a separate Last notification timestamp proves a verified delivery. Setup never invents that evidence.
3. **Location.** Add one active unbilled location. Choose **Load prices from Stripe** to import active AUD monthly per-unit licensed prices, then select the location and per-user fees by their names/amounts. This explicit action reads every page before replacing the cached choices; it never creates or modifies provider prices. Create/reuse a paying customer in OpStack. Select Stripe Tax only after configuring provider registrations and product tax codes. **Save & continue** saves all plan drafts. Advanced retains manual Stripe IDs, existing subscription links and per-location automatic settings. Each location has its own two-item subscription; shared payers reuse the same customer.
4. **Checkout.** Choose **Review checkout** to review current fees/counts/tax, then explicitly create a hosted link. Open/copy it for the customer to complete. Choose **Done**, then **Check checkout status** to read authoritative Stripe results and link the completed subscription. Links expire in about one hour. Test card details appear only in Sandbox. This check never approves quantities or enables automatic updates. New subscriptions/charges never start from browsing or saving a plan. Existing active/trialling subscriptions show their linked status; unresolved payments/statuses remain guarded by the existing review.
5. **Automatic updates.** Choose **Review & enable updates**. This explicitly saves the selected plan's automatic-count flag before the read-only financial review. **Approve & enable updates** uses the existing reviewed/idempotent Stripe quantity writer, then enables the global automatic setting using a separate revisioned save. The review discloses that previously approved automatic plans will also resume. Changing quantities prorates on the next invoice. A confirmed provider update is not replayed when only the final save needs retrying; unknown writes retain the exact body/key. Changed configuration requires another review. Progress resumes from the saved approval/global flags after reopening.

Use the location picker to work on another plan without redrawing its unsaved fields. The wizard exposes only one location editor at a time. Read-only navigation does not contact Stripe. Save progress and Discard unsaved changes retain the existing guarded settings retries. Pending provider/customer actions remain visible for exact retry on every step. Invoice results remain under Monthly report → Collections; choose Sandbox explicitly for test data.

Create and manage prices, payment methods, receipts, dunning, customer terms, tax registrations, refunds and cancellations in Stripe. Customer portal actions remain explicitly reviewed; disable customer quantity/price changes there if OpStack manages those quantities. Unsupported fractional-cent, tiered/usage-based/transformed or non-monthly/non-AUD prices are excluded from the picker. Historical/unknown fees and existing linked references are retained, never silently changed to a suggested price. Repeat setup in Live with its separate objects after testing.

## Per-network billing settings

Each network card in Console → Networks has a **Billing** button (owners only). It opens that network's billing settings for the chosen environment (Live by default, or Sandbox). Everything still uses the one platform Stripe account.

- **Automatic user-count updates.** This switch belongs to the network. Off pauses the app's quantity changes for every location in the network; Stripe keeps invoicing existing subscriptions. On (the default for networks never saved here) lets approved plans with automatic updates follow user counts as before. The global setting in Billing still has to be on, so it works as a master switch. The background check rereads the switch before every update.
- **Defaults for new location plans.** Choose a default payer (a saved Stripe customer), monthly location fee, fee per user (from the loaded price list) and Stripe Tax default. Billing → Location prefills new plans for that network's locations with them, and they can still be changed per plan.
- **Locations.** The network's locations are listed with their plan status, payer, rates, counted users and whether updates are automatic. Tick **Create draft plan** for active locations without a plan to create unapproved drafts from the defaults. Drafts never contact Stripe; finish checkout and automatic updates in Billing as usual.

Saving is revision-checked, uses a retry reference, records a console audit entry, and is blocked while a Stripe action is waiting for a retry. Opening or saving this dialog never calls Stripe. Sandbox and Live keep separate network settings.

## Customer records and retries

Customer creation is owner-only and separate from subscription/checkout approval. It requires a saved, tested Stripe connection, but can be used while location plans are still drafts. New customer details are sent only after review; neither page reads nor review creates a provider record. Creating a customer does not send an invitation, create a subscription or start charging. Company and staff records are never used as a guessed legal payer or billing contact.

The app retains explicitly supplied billing details privately in `opstack/stripe.json` for duplicate matching and exact retries, separate from imported financial snapshots. Owner settings expose the created customer name, email and ID for reuse; reports and activity logs do not expose its address/contact details. Sandbox and Live customer libraries stay separate. Changing details in Stripe requires a fresh review; a verified deleted customer can be explicitly replaced. Existing location/subscription links never change automatically.

Unknown results reserve and freeze the same shared Stripe write queue as subscription actions. The dialog offers **Retry the same creation**; after refresh/restart, **Retry customer creation** remains visible above the plans. Retries reuse the stored body and idempotency key for up to 23 hours, including after a server restart. A completed creation remains reusable even if its original plan draft was discarded. Saving the location's link with Continue or Save progress is still explicit. If another owner changed billing settings, retain/review drafts and reload before saving rather than overwriting their change.

## What counts as a user

Activated tenant accounts with a saved membership at an active billed location count. Pending invitations, devices, platform support identities, archived locations and suspended networks do not. Within one Stripe Customer and network, a shared account counts once: its home location takes priority; otherwise stable location ID order chooses a linked location. Separate tenant accounts/networks are separate identities; different paying customers count their own memberships. The price and count preview exposes the allocated total without staff personal/payroll information.

The app checks every minute while running. It decreases quantities before increasing them when shared staff move. An increase is blocked until the other locations' saved quantities are reviewed/reduced. Only explicitly approved plans with active approving owners and automatic updates enabled are eligible. Deactivating automatic updates stops app adjustments, not Stripe's recurring invoices. Archived locations receive zero base/user quantities on the next enabled check; cancelling a subscription is a separate Stripe action. Quantities reflect sync time, not a reconstructed per-day usage ledger.

Unpaid, cancelled, incomplete or otherwise unsupported subscriptions withhold quantity changes. Resolve their invoices/status in Stripe first. The Console retains the last report and shows errors. Stripe can still retry an unpaid invoice according to its own settings. Subscriptions must be dedicated to OpStack: do not mix unrelated charges or edit quantities externally while app automation is active.

## Monthly report

Sales uses saved **full-month recurring estimates**, one location fee plus its allocated users, for linked Live plans. Estimates update only after confirmed quantity actions. Previous monthly snapshots remain fixed; unknown historical user counts stay unavailable. Pre-connection months retain their existing manual fees. Unlinked locations retain manual fee entries. These estimates exclude proration, credits, discounts and tax additions; actual invoices are in Collections. Tenant weekly expenses, ordering and payroll are unaffected.

Collections imports complete paginated invoices and refunds, retaining the previous snapshot on failure. AUD only. Linked paid invoices appear in their payment month in Melbourne time; open and uncollectible invoices use creation month. Paid-outside-Stripe amounts are separate. Succeeded refunds use their creation month and invoice charge link. Unmatched records remain excluded with a visible count. Reports are invoice outcomes, **not bank reconciliation, payouts, Stripe fees or GST returns**; paid invoices may use customer credits. Use Stripe's financial reports for those figures. Historic subscription-to-location links are retained. No customer names, bank details, mandate or card data is stored in reporting snapshots.

## Retry and operational boundaries

Provider writes are explicitly reviewed, durably reserved and sent with a stable Stripe idempotency key. Unknown results freeze further writes/settings; Retry pending action replays the exact stored body/key, including after refresh/restart, for up to 23 hours. Never create another checkout to work around an unknown result. After that window, or if the approving owner is replaced, inspect Stripe and reconcile the private reserved action with support before resuming. This protects against duplicate charges; automatic jobs do not replay ambiguous money actions.

Webhooks verify the unmodified body, environment and timestamped HMAC (five-minute tolerance), persist deduplicated event IDs and fetch authoritative results. Periodic refresh is every 15 minutes. No provider call occurs on page/report reads, migration, startup with no enabled connection, or old GoCardless routes (410). All owner writes retain native same-origin JSON, CSRF and account-version checks. Test with synthetic Stripe fixtures only; never use live keys or customer data in tests.
