# Optional checklist features

Checklists → **Features** (`/ops-management#features`) switches nine optional features on or off for the whole company. Settings live in the company's private `checklist-extras/<companyId>.json` with everything these features save. Reading needs checklist viewing. Changing a switch needs checklist management, all-location access, CSRF and the current `revision`. Omitted switches are on. Turning a feature off hides it and stops its effects without deleting saved details.

Server: `checklist-extras.js`. Shared model (features, starters, answer text, score rule): `public/checklist-extras-model.js`. Page script: `public/checklist-extras.js`, which adds the Issues, Logs, Trends, QR codes and Features views to the Checklists sidebar and hooks into the native page through `ops-rendered` / `ops-run-opened` events. Every read goes through the native checklist store's `runFacts`, so company, location, kiosk, planner audience and step limits stay enforced, and reads never write.

| Feature | Behaviour |
| --- | --- |
| **Issue follow-ups** (`issues`) | Each failed check (pass rule) on a completed run in the last 60 days is an issue. Anyone who can open the run sees it in **Issues**. Managers (`ops.manage`) set an owner, a due date and Open/Resolved (a note is required to resolve). Saves are revision-checked (`PUT /api/checklist-extras/issues/:runId/:stepId`). If the checklist's QR station names equipment, the issue links to Equipment to report a problem. |
| **Missed and failed alerts** (`alerts`) | The notification bell's `checklist-alerts` category shows managers today's missed checklists and open failed checks at their location. It also tells owners about issues assigned to them and completers about redo requests. |
| **Manager review** (`review`) | In a completed checklist, managers **Approve** or **Ask for a redo** (comment required). Runs stay immutable; the completer is notified. History cards show an Approved / Redo requested chip. |
| **Logs and PDF export** (`foodSafety`) | **Logs** charts any Number step (for example temperatures) over 7–90 days, with its pass-rule safe range shaded and out-of-range readings in red. **Print / Save as PDF** in a completed checklist opens a printable page with answers, rules, corrective notes, photos, times and the review. |
| **Assign from the roster** (`roster`) | Per plan (Features → Assign from the roster): anyone rostered on during the checklist window, the opening shift (earliest start) or the closing shift (latest finish), from the published roster (`rostering.publishedOn`). Checklist cards show "On shift: …" and those people get a notification. This names people; it doesn't change who may complete the checklist. |
| **QR codes** (`qr`) | Managers add a station (plan, location, name, optional equipment) and print its QR code (`/api/checklist-extras/stations/:id/qr.svg`, made with `qrcode-generator`). Scanning opens `/ops-management?scan=<token>`, records who scanned and when, and opens that checklist. The reader shows today's scans. Deleting a code stops it working. |
| **Shift handover notes** (`handover`) | At the end of a checklist, **Note for the next shift** (≤500 characters, explicit Save note). The latest note from the past 7 days for that checklist and location shows at the top of the next run. |
| **Starter templates** (`starters`) | Checklist builder → **Add a starter template**: Opening, Closing, Cleaning and Food safety temperatures, created through the normal checklist API (content only; set plans and locations in Plans). |
| **Score trends** (`trends`) | **Trends** shows each store's weekly average score: the points percentage for scored checklists, otherwise the share of checks that passed. It ranks stores on the last four weeks with gold, silver and bronze places. Head Office Home shows the same leaderboard (`public/home-checklist-scores.js`). |
