# Project instructions

- Run relevant tests whenever adding or changing application behavior. Run `npm test` before delivering code changes.
- For interface or navigation changes, also check the affected interactions in desktop and phone browsers, including relevant permission levels.
- Use isolated temporary data for tests so existing accounts, settings and orders are preserved.

- Ops management content belongs to the selected company. Keep the builder in two stages inside the selected checklist: Checklist for content, then Planner for the Planners, Locations and Assignees grouped popups. Do not show those groups in the Checklist stage or add a separate planner page. Flush and validate content before entering Planner, and preserve fields and open step options when switching stages. Keep the collapsible live phone preview desktop-only, use the same mobile checklist fields and appearance, and isolate its inert controls/readers from real runs, autosaves and uploads; never create records from previewing. Use the supplied phone-frame asset inside the original 340 px preview panel. Keep the desktop builder headers, toolbar and cards compact. Anchor the preview to the top of the desktop content viewport while preserving the lower edge it had beside the builder. Reserve its 340 px right column for the headings and toolbar as well as the editor, including the collapsed 42 px state. Centre and maximise the phone within the panel width and height so its whole frame stays visible. Fit against the builder’s stable document position, and recalculate after resizing and relevant content-size changes without rebuilding editor fields or changing preview size during page scrolling. Preserve scrolling inside the preview and avoid horizontal page overflow. Keep planner type cards and timing rows compact, with controls visible together on desktop and touch-sized on phones. Each planner retains its own locations, permission-level audience and timing. Preserve anchored daily/weekly/fortnightly/monthly/yearly periods, month-end and leap-year dates, legacy calendar-week identities, and Melbourne start/due/overnight active-hour behavior. Active windows gate new starts using the server clock and cannot be bypassed with a past date; allow already-started work to finish. Enforce the current planner audience by stable role ID for tasks, history, record reads/writes and private media, in addition to existing company/location and Ops permissions. Management access allows configuring a checklist without bypassing its record audience. Keep all three grouped edits in the selected planner’s serial autosave and restore checklist focus on close. Require access to every location used by any planner (including paused planners) for content edits, and to every existing/new assigned location for planner edits. Migrate legacy templates to stable planners without rewriting records; deduplicate scheduled starts by planner/location/period, not just template. Keep content/planner autosaves separate and retain their snapshots. Keep the active header date-led, with the selected location, Melbourne clock, previous/next-day controls, app dropdown sorting and status/priority filters. On-demand runs must choose authorised existing manual planners, respect active windows and completion permissions, and preserve request IDs on retries; opening the picker creates no record. Keep active checklist cards narrow (130 px grid minimum), with compact heading/filter spacing and New checklist available only in Checklist builder. Active checklist cards open across their whole surface, with keyboard access and focus restoration, compact saved-response progress and a green completed state. Derive counts from the saved run snapshot, exclude instructions/sections, preserve optional blank answers, and automatically complete after every response step has saved and active editing/uploads finish; sections and instructions never trigger completion. Reminders are in-page badges, not external or background notifications. Require access to every assigned location for template edits; completion and file uploads/downloads require current company/location permissions. Preserve template snapshots and immutable completed records, revision conflicts, private photos and idempotent scheduled starts. Checklist schedules use Melbourne dates and Monday–Sunday weeks. Keep compact template card reordering separate from App edit layouts and preserve step IDs. Sections carry their following steps when dragged. Validate number precision, scoped user/location selections and private file/signature references on the server; preserve legacy step snapshots. Opened checklist runs use a desktop modal and fill the app viewport on tablets/phones; keep the persistent shell informed and restore navigation, focus and draft state on close/resize. Live green completion must inspect values without uploading signatures or saving answers. Save checklist answers and valid template edits separately through debounced, serial autosave; never redraw focused fields on an acknowledgement or overwrite revision conflicts. Keep final completion as a separate revision-checked request after autosave settles, retain manual completion for optional blanks, flush before leaving, and show pending/failed saves for unfinished or invalid fields. Never treat entered step titles, choices, answers or signatures as interface wording.

- Home sections are edited directly on Home in desktop App edit and saved company-wide in `home-dashboard.json`, independently from appearance and `layouts.json` ordering. Keep the fresh default, allowlisted section/link catalogue, the permission-aware desktop + shortcut picker in each Quick links heading, inline configuration, shared hold-to-drag and keyboard movement, automatic revision-checked saving, Undo and conflict recovery. Preserve legacy metric IDs/calculations and company appearance customisations. Fetch only configured, permitted widgets from scoped APIs; never acknowledge Comms, start checklists, punch clocks, create print batches or place orders from dashboard reads. Custom titles/notes and live values remain data for wording protection. Hide editing on phones and preserve the roster popup. Treat saved Home sections as custom formatting in legacy-default migration.

- Section resizing uses a bottom-right corner handle in desktop App edit, with arrow-key adjustment, Escape cancellation, company-wide autosave and Undo. Home dimensions belong to `home-dashboard.json`; other page dimensions share the revision-checked `layouts.json` store with ordering. Preserve dimensions when older clients save moves without sizes. Pack cards beneath shorter neighbours without rebuilding their contents, clipping data or changing phone layout. Add below inherits the selected Home section width and column. Preserve open Home configuration drafts when resizing or undoing geometry. Preserve default layouts on other pages until a section is resized. Keep appearance popup controls compact, common colour/scope choices direct, advanced target/group options collapsed and Save visible.

- App edit must not select, highlight or customise individual words, numbers or text styles. The one text exception is the Home greeting: clicking it or pressing Enter/Space in App edit opens the company-scoped greeting editor, preserving exactly one {user} placeholder and the real account name. Keep revision conflicts and desktop-only editing, and do not expose general Interface text or font controls. Backgrounds, images, icons and arrangements remain editable. The orange indicator uses a subtle rounded frame and floating “App edit mode” pill. Keep saved wording customisations working, and preserve their current linked/unlinked behavior when linking or unlinking appearance. Highlight and intercept clicks only for supported, visible editable parts, using the same eligibility check for hover, selection and target choices; skip disabled, readonly, inert and protected controls without falling back to their parents. Keep `public/wording-model.js` source checks shared by interface wording, individual overrides and linked overrides. Static labels receive sources on the server; declare dynamic UI labels with `appWording.label` or `data-app-template`, preserving placeholders and original values. Treat undeclared dynamic text as data. Preserve previously saved fonts, text colours and wording while editing surfaces; surface linking must not change text appearance or wording. Do not pass user, company, location, role or stock names through `interfaceLabel` as label keys.

- Invite new users by email from Users; recipients choose their own passwords through expiring, single-use setup links. Account setup emails use one platform-wide sender in Opstack console → Account setup emails, never location order-sending credentials. Legacy Head Office sender settings remain available only until the first Opstack owner is created. Preserve legacy sign-ins, custom permission levels, hierarchy and location restrictions. Store only hashes of setup tokens, and never expose tokens or sender secrets in API responses or logs; pending accounts cannot sign in or count as active network recovery owners.

- Keep Opstack owners/support separate from tenant roles. The first owner is created only through the server's `npm run opstack:owner` command; subsequent owners/support are invited through the console. Network Head Office permissions cannot grant platform authority. Support uses the server-only identity marker, never a customer password or employee record. Preserve separate network storage, existing root data, shared platform branding/email settings, cross-tab network checks, support attribution and immediate revocation. Personal employee PINs/private chat memberships are not impersonated. Test platform owner, support and tenant roles on desktop and phone.

- The main sign-in page finds the tenant network only after verifying credentials. Never return matching networks or user details before authentication. Keep explicit network-code links scoped, preserve legacy duplicates with a code prompt, rate-limit discovery, and clear stale support selection on normal sign-in. A tenant email (including an email-like username) belongs to one network; serialize the ownership check and account write across network creation, invitations and edits. Pending users and suspended networks retain ownership. Do not delete or merge pre-existing duplicate accounts or grant tenant users platform access.

- Opstack console Monthly report is owner-only platform revenue reporting. Derive location rows from registered networks, group by network and keep each location's dated recurring fee separate. Fee changes apply from the selected month without rewriting earlier months; new networks/locations appear from their Melbourne creation month. Keep platform expenses separate by month and separate from tenant sales/expenses. Preserve cents, blanks versus zero, optimistic revisions, unsaved expense drafts and owner-only API checks. Do not infer fees or collect payments from report edits.

Keep the shared Opstack logo/background, preserve each network's defaults snapshot, seed later companies from it (including new companies in legacy/customised networks), and never apply future-default changes over existing network or company edits. The versioned legacy migration updates only networks whose existing companies have no custom colours, fonts, backgrounds, images, logos, wording, layouts or App edit changes; one customised company protects the whole network. Require explicit, revision-checked lesson acknowledgements and server-graded quiz attempts with idempotent request IDs; never expose answer keys to learners. Preserve completed history, retry/conflict drafts, private rich lesson media and required Comms reading. Course authoring uses a fixed left options/editor panel and a fixed right live preview with a phone-width course. Keep headers, stage controls and Save/Publish in place while pane contents scroll independently, without scrolling the document. Show every course section in the live preview; clicking a section or step selects its left-hand controls without rebuilding focused fields. Use the left Course outline with collapsible section groups, step icons and transition entries; select only the matching section, block or transition properties below. Keep all writing, formatting, question settings and answer keys on the left. The scrolling canvas exposes only insertion + buttons and movement grips as authoring controls. Insertion + buttons open the left Add a block toolbox and retain a stable before-block or before-section anchor; content, question and authorised Library insertions must preserve existing IDs and order. Small screens switch Editor/Preview panels while preserving the draft. Keep all course settings, content/question editors and Planner access on the left. Test course changes only the right preview to learner transitions and never creates records. Keep stable section IDs, ordered content/question references, bounded backgrounds/text colours, safe fonts/text sizes, reading durations and transition labels in immutable published snapshots. - Shift clock is a shared signed-in-page popup, not a navigation page. Verify a fresh staff PIN on the server before revealing each clock stage’s actions. Preserve actual timestamps and approval history; never store raw PINs in API responses, browser storage or audit records. Never auto-create clock punches or end breaks from timers.

- Clock PINs derive from the last four digits of each user’s phone number. Enforce unique endings across all companies when saving a phone, preserve leading zeroes, and require phone setup before clocking. Keep phone editing under existing user-management permissions.
